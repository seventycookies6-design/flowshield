**VM:** Windows 11 Pro 25H2, clean checkpoint, no prior FlowShield.
**Requested for:** the standing step 7 (in-app update) gap.

**Partial.** The fresh install is confirmed good on 1.0.7. The update test could
not run, for a reason that is not a bug — see *Blocked* below.

## Worth knowing

Immediately after a silent install and **before the app is first launched**,
both `HKCU\Software\Classes\flowshield` and the Run key are absent. This is not
a regression — the installer does not write them; the app does on first launch.
It matters for how step 2 is tested: checking the protocol handler straight
after an unattended install will always look like a failure. The original
#53 pass checked it with the app running, which is the correct order.

## Blocked

**Step 7 (in-app update) could not be run.** `DesktopApp/Services/UpdateService.cs`
hardcodes the feed to the public repository:

```csharp
private const string ReleaseFeed = "https://github.com/seventycookies6-design/flowshield";
```

So a genuine 1.0.7 → 1.0.8 update needs 1.0.8 published as a **public GitHub
release**. A locally built 1.0.8 exists and installs, but the updater cannot see
it. `GithubSource` is constructed with prereleases disabled, so a pre-release
would not be visible either without a code change.

No release was published. `CLAUDE.md` assigns releases to the repo owner or
whoever they name, and `LEGAL_CHECKLIST.md` asks for a re-check before every
release — items 1.1 (seller identity still shows `[operator name]`,
`[registered address]`, `[support email]` in `legal.html`), 1.2 (Stripe business
profile incomplete), 4.6 (refund contact) and 11.5 (no licence DB backup) are
open and marked OWNER.

**Recommendation:** fold step 7 into whichever release is cut next for its own
reasons, rather than cutting 1.0.8 to unblock a test.
