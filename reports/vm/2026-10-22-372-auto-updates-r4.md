## Problems

- **The host disk, not the product, ate this round.** `G:` is on Disk 1, a USB hard drive shared with `M:` and `K:`. `M:\salad\wsl\ext4.vhdx` (the Salad app's WSL disk) was being written throughout, at times with thousands of flushes (Hyper-V counter: write 1.5 MB/s, flush count 6676 at 11:21). Host counters, Disk 1 (sampled with `Get-Counter`, host time):
  - 10:57: queue 10–16, 7–33 MB/s, G: latency 0.11–0.18 s per transfer (`G=4.4/5.9/4.3/4.2/7.7 MB/s`, `M=0.5/0.8/7.2/2.9/0.06 MB/s` at 11:32:23–48).
  - 13:49 (the worst stretch): G: latency **0.79–1.31 s**, 130–240 KB/s, **4–9 transfers/s**, queue 7–22, with M: at 4–27 MB/s (`235826 B/s lat 0.98 q 7`, `160001 B/s lat 1.06 q 12`, `81044 B/s lat 1.76 q 22`).
  - 13:49:52–13:54:08, 16 s apart: `lat=0.013 iops=141`, `0.011/190`, `0.009/241`, then **`1.237 s / 12 iops`**, **`1.606 s / 7`**, `0.314/40`, **`0.293/5`**, **`0.843/5`**, `0.131/54`, `0.437/16`, **`0.334/2`** (M: 12 KB/s), **`1.249/8`**, `0.026/71`, **`0.609/7`**, `0.06/10`, back to `0.017/115` and `0.010/208`. The spikes mostly coincide with `M:` writing (e.g. 1.237 s at M 522 KB/s, 1.249 s at M 1.9 MB/s), but not all do: 0.334 s and 1.261 s occurred with `M:` near 0.
  - `disk1-samples-final.txt`, 14:02–14:06: mostly `0.006–0.046 s`, 40–250 IOPS, with one `1.261 s / 2 IOPS / 126 KB/s` at 14:04:06 while `M:` was 0.
  - Even in the quiet stretches, new executables in the guest stalled. With 4–7 MB/s of the guest's own I/O, Windows servicing (`TiWorker` 42 s CPU, `MoUsoCoreWorker`) and Defender's `MsMpEng` (146 s CPU) running, the guest was I/O-starved in ways that varied minute to minute. No `disk` 153/7 or `Ntfs` 50/55 event occurred; the drive stayed `Healthy`, and no other cause is established.
- **New executables hung in the guest.** `pythonw.exe` from a scheduled task sat for 28+ minutes at 3 MB working set with zero reads (main thread `Wait/Executive`); `python.exe -I -S -c "print(1)"` launched from PS Direct also failed to exit in 25 s. Adding a Defender path exclusion for `C:\Program Files\Python312` made the same command exit in **137 ms**, so Defender real-time scanning was the blocker for that executable. `FlowShield.exe` was blocked in the same way for 8 minutes even after its folder was excluded (hence the 13:00:46 → 13:08:57 gap before the first log line). Network was fine (DNS, TCP to Microsoft endpoints connected in 16–109 ms). The app's own log shows the stalls: `schedule tick 237 s late`, `162 s late`, `317 s late`.
- **UI Automation was unreliable under this load.** pywinauto's full-tree searches and `Invoke` calls timed out (above). Round-3-style long waits were applied (`Timings` 120 s, 15–30 minute `wait` deadlines, a direct-UIA `FindFirst` helper, retries) and still failed on the last attempts; per the orchestrator's time-box, no further harness changes were made.
- **Monitor lapse and false stop**: see "Bench changes". No other storage or Hyper-V event: host System log had **0** `disk`/`Ntfs`/`storport`/`stornvme`/`volmgr` events from 10:08:13 to 14:11; the only Worker critical event was the WSL one above (10:09:08); VMMS **20790** (Error) on each restore (10:08:43, 10:09:16, 10:12:05, 11:04:03, 14:11:35), message `Failed to set security info for 'G:\HyperV\FlowShield-Lab\VMs\FlowShield-Lab\FlowShield-Lab.vhdx': 'Access is denied.
